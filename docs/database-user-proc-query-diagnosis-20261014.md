# user proc 总数为空：诊断与可用请求

日期：2026-10-14。对应任务：定位此前 `user proc` 在查询总数接口中返回空表的问题，验证可用请求；未实施堆叠图代码。

## 1. 结论

**不是没有记录，也不是简单的大小写或 URL 空格编码问题。此前查询策略假设“命令行的 Id 可以直接作为 getTopGroups 的单命令筛选条件”，该假设在本次 user proc 样本中不成立。** 即使使用 `getTopGroups` 自己返回的 `USER PROC` 行标识，单命令筛选仍为空。

已验证可用方式：保持父实例范围，将命令维度设为 `QUERY_COMMAND=?`，使用 `getTopGroups` 原生分组，一次返回该实例各命令的实际 `QUERY_COUNT`。两个实例、两个固定时间窗共四组结果，分项计数之和均精确等于父实例计数，重复查询的分类和数值一致。

这解决了后续堆叠图获取真实查询数的阻塞项。**单命令具体值筛选与原生分组的接口行为差异已经复现，服务端内部解析根因尚未确定。** 本地参考项目没有 236 的数据服务实现和日志，不能把它进一步断言为某个解析器、存储字段或服务端版本的缺陷。

## 3. 假设与实际结果

| 假设 / 对照 | 观察 | 判断 |
| --- | --- | --- |
| 带空格的命令值需要引号 | 原始 `user proc`、单引号、双引号均为空；SELECT 原始条件有计数，双引号条件反而为空 | 加引号不是有效修复，不能修改全部请求来加引号 |
| 空格编码错误 | `%20` 与 `+` 两种合法编码均为空；业务参数和外层代理 URL 的编码往返一致 | 未发现 NOP 构造阶段丢失或重复解码的证据，替换空格编码无效 |
| preselect 干扰筛选 | 保留 `preselect=""`、移除参数、设为空字符串均为空 | 不能通过调整该参数修复本次问题 |
| 命令类别大小写不同 | 两类接口分别返回 `user proc` / `USER PROC`；仅改成大写、混合大小写仍为空 | 大小写差异是观察到的现象，不是已证实根因 |
| 运行统计有另一个可直接复用的标识 | 运行统计的 user proc 标识与命令统计相同，复查总数仍为空 | 换用运行统计行标识不能直接修复总数查询 |
| 数据实际存在，但单值筛选路径不兼容 | 同一父实例范围的 `QUERY_COMMAND=?` 原生分组返回真实 user proc 计数，运行统计命令分支亦返回相同计数 | 已证实数据存在；应改用已验证的原生分组获取矩阵 |

最初发现大小写差异后，继续用仅改变大小写的请求验证，结果推翻了“改成大写即可修复”的猜测。不能把全部 `selection` 转为大写；这还可能改变实例等其他条件的业务含义。

## 4. 最小复现与已验证请求

### 4.1 失败复现

共同参数如下；`selection` 使用实例内命令行实际返回的完整条件：

```text
type=getTopGroups
start=1791820800
end=1791907200
top=100
topMetric=QUERY_COUNT
visibleColumns=QUERY_COUNT,QUERY_COUNT_RATE
selection=<父实例范围> QUERY_COMMAND=user proc
preselect=""
json=true
```

上面的 `<父实例范围>` 是结构示意，不是可直接粘贴的完整条件；实际测试保留服务端返回的节点、实例范围和连接语法。结果为合法空表。使用原生分组返回的完整 `Id`（命令值 `USER PROC`）亦为空。

命令统计使用相同原始完整条件，`getTroubleshootData / ScriptTabularDataSet / Query Command` 则返回 1 行非零速率。运行统计同一命令分支还实际返回查询数。这排除了把“空表”直接解释为该实例没有此类记录。

### 4.2 可用请求

使用相同 `getTopGroups` 参数，只把命令维度设为分组占位符：

```text
type=getTopGroups
start=1791820800
end=1791907200
top=100
topMetric=QUERY_COUNT
visibleColumns=QUERY_COUNT,QUERY_COUNT_RATE
selection=<服务端返回的父实例范围> QUERY_COMMAND=?
preselect=""
json=true
```

本次构造是从服务端实际返回的命令条件中，将末尾已识别的 `QUERY_COMMAND=user proc` 替换为 `QUERY_COMMAND=?`，保留其他条件及连接方式不变。不是从实例名称拼接父范围，也不是把任意完整条件进行大小写转换。后续执行器需要验证条件结构，不能用不受约束的字符串替换处理 SQL 或其他维度。

业务 URL 的参数分别编码，再把完整 URL 编码后交给本地平台代理：

```js
const target = base + '?' + Object.keys(params)
  .map(key => encodeURIComponent(key) + '=' + encodeURIComponent(params[key]))
  .join('&')
const proxy = '/NetInside/admin/datasource.asp?m=proxy&url=' + encodeURIComponent(target)
```

该请求返回 `Query Command`、`Transactions (#)`、`Transaction Rate (#/min)` 等字段；响应的命令类别为 `SELECT`、`INSERT`、`UPDATE`、`DELETE`、`USER PROC`。这是一个父实例的原生命令分组表，不是一次取得所有实例的二维矩阵；仍需对所选父实例分别请求。

## 6. 后续实施决策

后续“实例 × 查询命令 × 查询数”采用：

1. 固定数据源、节点和时间快照，取得真实父实例范围。
2. 逐父实例通过 `getTopGroups / QUERY_COMMAND=?` 请求命令计数。
3. 独立取得父实例计数，并校验分项和；失败、缺失、截断或合计不符时阻止完整总柱。
4. 使用原生命令类别建立稳定键，不把不同接口的显示标签或完整行标识直接混用。

不再采用“从命令统计取得每个命令 Id，再逐条向总数接口补查”的查询数方案。原有命令统计和运行统计使用自身已验证的接口，不因本次发现而全局改写其条件。

本次证据足以继续实施查询数矩阵执行器，并在每次刷新时保留合计校验。它不自动证明其他指标、其他分析组合、所有节点和所有时间的可加性，也不等于图表绘制、保存或预览已验收。

如继续追查服务端内部原因，可用本报告的相同条件复现对照，核查 236 对具体命令值筛选与 `?` 分组的解析路径；需 236 数据服务实现或对应诊断日志。已有可用分组链路，不必通过猜测命令别名、强行补零或计算“其他”推进绘图。
