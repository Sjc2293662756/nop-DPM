## 2. 实际请求构造

所有请求的业务目标相同：`https://101.254.114.236/webservice/NetInside`。下表为编码前参数；动态 `selection` 使用上一步响应的原始 `Id`，不从实例显示名称拼接。

### 2.1 查节点

```text
type=getTopGroups
start=1791820800
end=1791907200
top=100
topMetric=QUERY_COUNT
visibleColumns=QUERY_COUNT,AVG_FINAL_RESP_TIME
selection=DB_NODE_ID=?
preselect=""
json=true
```

返回 3 个节点：238、239、240，查询数分别为 64,967、60,162、58,876。选择实际返回的 239 节点标识继续查询。

### 2.2 查实例，再查该实例的命令

```text
type=getTroubleshootData
start=1791820800
end=1791907200
top=100
dataType=ScriptTabularDataSet
dataTypeLabel=DB Instance
visibleColumns=FINAL_RESP_TIME,DB_INSTANCE,QUERY_TEXT
hiddenColumns=QUERY_COUNT
selection=<节点范围条件>
aggrField=QUERY_TEXT
label=InstancesData
json=true
```

命令请求保留同一时间范围和固定请求字段，只修改：

```text
dataTypeLabel=Query Command
label=CommandsData
selection=<实例行返回的原始 Id>
```

节点全局命令基线则使用节点范围条件。两个实例的原始 `Id` 均包含 `DB_NODE_ID` 和 `DB_INSTANCE`；命令行的 `Id` 进一步包含 `QUERY_COMMAND`。

实例、命令的基础模板对照了原 DPM 的 `js/script.js` 中 `DBTrouble` 配置。原模板是单维分析；本轮通过实际请求单独验证了父实例条件可以限定命令结果，不把原模板当作交叉能力的证明。

### 2.3 按同一筛选范围查实际查询总数

```text
type=getTopGroups
start=1791820800
end=1791907200
top=100
topMetric=QUERY_COUNT
visibleColumns=QUERY_COUNT,QUERY_COUNT_RATE
selection=<实例或命令行返回的原始 Id>
preselect=""
json=true
```

只在结果恰好返回一个节点行且具有计数字段时接收该范围的查询数。没有用速率乘时间推算计数。

构造业务 URL 时分别对参数名称和值调用 `encodeURIComponent`，再将完整 URL 编码为平台代理的 `url` 参数：

```js
const target = base + '?' + Object.keys(params)
  .map(key => encodeURIComponent(key) + '=' + encodeURIComponent(params[key]))
  .join('&')
const proxy = '/NetInside/admin/datasource.asp?m=proxy&url=' + encodeURIComponent(target)
```

这是两个 URL 层级各自的编码，不是把服务器返回的筛选条件重复解码或改变条件内容。本轮原始标识没有百分号编码片段或 HTML 实体，未执行解码候选。

## 4. 查询速率的真实交叉结果

主区间结果，响应列头为 `Transaction Rate (#/min)`，下表单位为次/分钟。

| 命令 | 实例 A | 实例 B |
| --- | ---: | ---: |
| select | 4.381 | 20.071 |
| insert | 0.465 | 未返回 |
| update | 0.500 | 未返回 |
| delete | 0.508 | 未返回 |
| user proc | 3.903 | 11.951 |
| 已返回分项合计 | 9.757 | 32.022 |
| 父实例速率 | 9.757 | 32.022 |

“未返回”不是接口明确返回 0，尚未据此补零。主区间父子速率合计除 JavaScript 浮点运算误差外一致，两个父实例合计为 41.779。

实际父查询数除以区间分钟数，与父速率按三位小数展示的结果相符：

| 区间 | 实例 | 实际查询数 | 父速率 | 子分项速率之和 |
| --- | --- | ---: | ---: | ---: |
| 24 小时 | A | 14,050 | 9.757 | 9.757 |
| 24 小时 | B | 46,112 | 32.022 | 32.022 |
| 6 小时 | A | 3,560 | 9.889 | 9.889 |
| 6 小时 | B | 11,467 | 31.853 | 31.852 |

第二时间窗 B 出现 **0.001 次/分钟**的输出差。主区间返回量速率也出现 A 的分项合计 1.583 对父值 1.582、B 的分项合计 16.660 对父值 16.661，单位为 kbytes/min。

这些差值可能来自分别舍入，但本轮没有取得服务端舍入或聚合契约，不能把该推测写成已确认原因，也不能任意取整或设置容差使其通过。查询总数与时间窗对得上是分母一致的样本证据，仍不能替代全部分项的计数和口径验证。

## 5. 实际查询总数的缺口

主区间补查结果：

| 命令 | 实例 A 的查询数 | 实例 B 的查询数 |
| --- | ---: | ---: |
| select | 6,309 | 28,902 |
| insert | 669 | 未查询：命令列表未返回该分项 |
| update | 720 | 未查询：命令列表未返回该分项 |
| delete | 732 | 未查询：命令列表未返回该分项 |
| user proc | 空表 | 空表 |
| 父实例实际查询数 | 14,050 | 46,112 |

两个父计数合计 60,162，与本轮节点查询数一致。但 `user proc` 的子计数缺失，两个实例都不能完成完整的分项计数守恒验证。

`user proc` 边界对照进一步确认：

- 同一原始命令 `Id` 在 `getTroubleshootData / Query Command` 中返回 1 行、有非零速率，与原命令表对应行一致。
- 该 `Id` 在 `getTopGroups / json=true` 中重复返回合法空表。
- 改用同一筛选条件的 `csv=true` 返回空正文，不是通过换格式就能取得计数。
- 返回条件中的命令值是未加引号的 `user proc`。含空格是待核查线索；原始条件已在命令统计中有效，不能直接判定为 NOP URL 编码错误。

这说明两类接口对同一命令范围的处理不一致，具体根因尚未定位。不能把空表解释为零，也不能用“父计数减已知分项”冒充服务端返回的 `user proc` 计数。

候选显示字段对照使用 `visibleColumns=FINAL_RESP_TIME,DB_INSTANCE,QUERY_TEXT,QUERY_COUNT` 并清空 `hiddenColumns`：实例表与 A 的命令表仍没有返回查询数，B 的命令表首次返回 `null`，重复复查恢复为 2 行但仍无查询数列。该方案没有通过取得查询数的验证；不据此替换现有生产请求字段。

## 6. 数量参数与异常观察

| 查询 | top=1 | top=100 | top=1000 |
| --- | --- | --- | --- |
| 实例列表 | 1 行 | 2 行 | 本轮返回 `null` |
| A 的命令 | 1 行 | 5 行 | 5 行，分类/数值指纹与 top=100 一致 |
| B 的命令 | 1 行 | 2 行 | 2 行，分类/数值指纹与 top=100 一致 |

`top` 会截断命令集合，不能把用户的主分类数量直接套用到分项数量。不能把 Top 1 的柱子称为实例总量，也不能将未返回分项补为零。

`top=100` 与 `top=1000` 的命令结果一致，提供当前样本的稳定性证据；接口未返回明确的完整性标记，不能仅凭“行数小于 top”推广为所有节点、所有时间和所有命令均完整。

两次 `null` 来自不同候选请求：实例 `top=1000`、B 的命令显示计数字段对照。B 的显示字段对照复查已恢复数据，不能认定为固定参数限制；实例 `top=1000` 仅取得一次异常观察，尚未重复定位。本轮分别保留异常事实，不解释为无数据或请求成功。

边界重复复查中，正常基线、两个 `user proc` 命令统计及其总数空表的分类/数值指纹均与前一轮一致；CSV 仍为空正文。核心计数缺口没有因重新请求而消失。
